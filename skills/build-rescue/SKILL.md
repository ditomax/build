# rescue — Stage 4

You are the **maintenance crew**: you make the codebase simpler without changing what it does, and you report where concept and code have drifted. Read `../../RULES.md` first (§10 binds you); the process is `../../MANIFEST.md` Phase 10 and "Concept ↔ Code Synchronization".

**Input:** `<FEAT>/20-concept.md`, `<FEAT>/30-synthesis.md`, `CONTEXT.md`, `decisions/`, `agent-testing.md` (or a legacy `test_tooling.md`), the layout ADR, `code_root`. **Output:** `<FEAT>/40-rescue.md` (a new `.vN` per round) from `templates/40-rescue.md`; refactored code under `code_root`. **Budget:** `budget_min.rescue`; `budget_refactors` = 5 with git, 2 without.

Lineage: MANIFEST Phase 10; maquette-harden (one commit per fix, revert on regression).

## Opening

Two sentences: a maintenance round — find what got tangled, untangle the most valuable pieces one at a time, and say what the concept must learn from it.

## Sequence

0. **Round kind.** The Director has asked the review triggers (R0); write them into §0. Every error caught in operation by a default exception handler or the entry-point backstop is classified with the ignore test and named for the concept redo (a missing scenario → a row, a missing hazard → H and SC, harmless → E-<FEAT>-H, or a bug fix). An incident → `kind: incident`: fill *Incident analysis* (CAST-light) before the scan — what happened, which loss, which control loop failed (missing SC · SC not enforced · feedback missing · process model wrong · conflicting controllers · authority too wide), why the structure allowed it (no blame on persons or the model), the new or changed SC with *Enforced by* now → target. Every new SC is a concept change: name it for the redo, with a regression test. Otherwise `kind: maintenance`.
0a. **Secret audit** (§1b, `templates/repo-hygiene.md`). Every round: A3 — are the repository-hygiene controls still in place (H1 checks, H5 test, H6 hook installed in this clone, H7 answer)? An **audit round** (`kind: audit`, the user's word "audit", or an incident involving a secret) runs A1–A4 in full and, besides step 0b, nothing else: ask **RA** first (gitleaks is an install), then scan the full history of all branches with redaction (A1), the allow lists with `tools/secret_check.py scan` (A2, also lists overly literal entries with a generalized replacement), the controls (A3), and write the findings table (A4) — file, line or commit, pattern type, never a value, not even partly. Any secret finding → state the order: rotate first, then clean history (the user's job: `git filter-repo` or BFG, force-push, re-clone), then re-run the audit. Read-only throughout: you change, delete and rewrite nothing. Sections 2–4 of an audit round read "not relevant — audit round".
0b. **Error-handling audit** (§1c, RULES §16, `checklists/error-handling.md`). Every round, whatever its kind; read-only. Read the code against concept §11 *Error handling* in both directions. *Matrix → code:* per E row — is the detector there, does the code take the row's action, is the bound counted and the escalation reachable, is the event logged at the row's level and kept where the strategy says? *Code → matrix:* every place that handles an error maps to a reaction row, a requirement from a scenario answer (eliminate, prevent, limit), an operational requirement or an outside action's standing row — in the product's code (`try`/`except`/`catch`, error returns and status codes, retries, fallbacks, default values on failure, ignored results) **and outside it**: the framework's exception handlers and middleware, the scheduler's retry and misfire settings, library retry defaults (HTTP clients, database drivers), the container's restart policy, webhook senders' retries into the product. None → classify it with the ignore test (`checklists/error-handling.md` §12): a missing scenario → a row, a missing hazard → H and SC (concept redo), harmless → it belongs in E-<FEAT>-H; a handler that hides the error is a silent fallback (a UCA of type P). A catch-all is allowed only in the profile's action-boundary helper and at entry points; a outside action not running through the action-boundary helper (its standing row) or without its invariant checks right before it is a finding. *Source:* every E row names a constraint, a scenario, an operational requirement or *unexpected at <action>* (the harmless row the ignore test) — a row with none is a finding; every outside action's handling in code matches its standing row before, during and after its commit boundary. *Repeaters:* compare the retries and restarts actually configured (scheduler, container, libraries, queues, webhooks) and the product's own re-polls with intake I13 and the concept's action rows — a repeater that can run an action again which is not repeat-safe is a finding, even when it is switched off. A restart loop that resets an 'n in a row' counter is a finding. Matrix → code is confirmed by the row's escalation test, not by its comment tag. *Path walk:* walk from each supported entry point (CLI command, scheduled job, route, inbound webhook) through setup, configuration loading, dispatch and its confirmation, and every recovery write — including the path that repairs a lost completion signal (a heartbeat after an accepted send) — and name the shared failure domains on the way (one host, one database, one relay, one file system); an error before the handler is installed is a finding. *Convention:* the profile's error convention (`layouts/<profile>.md` §8) — a failure signalled by a value the caller can mistake for a result, context dropped on the way up, an error caught where no action can be taken. For each finding state its status with the evidence: *reachable* (called on a real path), *unwired* (no call site, no consumer of the configuration found) or *unverified* (external configuration or platform behaviour that cannot be checked here). Write the findings table. Every finding changes behaviour, so it is never fixed here (rescue preserves behaviour): name it for the Director as a concept redo (new or changed row) followed by a synthesis slice.
1. **Scan.** Read the concept's traceability matrix against the code: modules that exist but are not in §11, behaviour with no requirement, requirements whose module changed shape. List drift with IDs. Run `python tools/dev.py check` and list layout drift (RULES §15 L1–L5: dependency direction, deep imports, grab-bag names, unregistered top-level folders) and docs out of sync as findings. Read the fix journal of `agent-testing.md`: a cause that keeps coming back is a deepening candidate. Then look for deepening opportunities: interfaces that could be simpler, duplicated logic, names that left `CONTEXT.md`, dead code, modules doing two things; a very long file may be *suggested* for a split (guideline L6 — never a finding). A legacy build or adopted code that should move to a catalogue profile is one opportunity of its own, with its own ADR — offered, never required. Rank by expected gain × low risk.
2. **Propose.** Show the ranked table and ask: "which ones, in this order?" — one question.
3. **Apply, one at a time.** Run the full test suite before; apply the refactor; run it after. Green → keep (with git: commit, RULES §6). Any regression → revert immediately, record the reason, move on. Stop at the refactor budget or the time budget and say which.
4. **Reconcile.** Every kept refactor that changes a signature, module boundary or term is a concept change: list the exact sections; the Director schedules a concept redo (version bump). Add ADRs for decisions taken here. Update `agent-testing.md` if a tool changed (fix journal for anything a refactor broke and you repaired).
5. **Write** `40-rescue.md` and hand back per RULES §7 with: round kind, secret-audit findings count and control states, error-handling audit findings count (rows checked, handling sites without a row, convention breaks) (the Director updates *Repository hygiene* in `00-build.md`), kept / reverted counts, drift items, concept sections to update, and for an incident the SCs to add or change.

## Anti-patterns

| Don't | Do instead |
| --- | --- |
| Refactor and add features in one go | Behaviour-preserving only; features are slices |
| Batch several refactors into one commit | One each; revert is cheap only when isolated |
| Fix drift by editing the concept yourself | Report the sections; concept redo is the concept stage's job |
| Keep a refactor with a red test "to fix later" | Revert; note it as an opportunity for the next round |
| Rename without updating `CONTEXT.md` | The dictionary moves with the code |
| Fix an error-handling finding inside a refactor | It changes behaviour: concept redo, then a synthesis slice |
